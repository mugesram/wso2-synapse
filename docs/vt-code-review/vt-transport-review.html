1. Executive Summary

The Virtual Thread (VT) transport is a fully blocking, Project-Loom–based replacement for the NIO PassThrough transport's request/response plumbing. The goal is to keep a blocking, easy-to-reason programming model per request while retaining the scalability of asynchronous I/O — by running each HTTP request on a lightweight Java 21 virtual thread instead of a shared platform-thread pool driven by an NIO reactor.

Why it exists. The existing NIO transport uses DefaultListeningIOReactor, asynchronous ContentDecoder/ContentEncoder callbacks, and a Pipe backed by a ControlledByteBuffer. This model is fast but complex: back-pressure, keep-alive, and chunked decoding all live in callbacks. VT lets us express the same flow as straight-line code (socket.read() → engine.receive() → response.write()) on a VT that parks instead of pinning a platform thread.

Design constraints that shaped the implementation

  • Reuse Synapse/Axis2 contracts. Listener still implements TransportListener; sender still implements TransportSender; worker still implements OutTransportInfo. Nothing above the transport layer changes.
  • Reuse SourceConfiguration and TargetConfiguration. These are full Axis2 lifecycle objects — recreating them would mean rebuilding JMX, metrics, WorkerPool wiring, and EPR-prefix logic.
  • Delegate HTTP protocol handling to HttpCore 5 blocking API. Parsing request lines, chunked decoding, keep-alive, and response serialization are too tricky to reimplement. HttpService does this and exposes ClassicHttpRequest/ClassicHttpResponse.
  • Replace HttpCore 4 NIO sender with HttpClient 4.5.x blocking client. The outbound path needs a blocking client that plays nicely with a VT — CloseableHttpClient with PoolingHttpClientConnectionManager satisfies this and exposes InputStreamEntity for zero-copy body streaming.
  • Zero-copy streaming path. When no content-aware mediator runs before <call/>, the raw client socket InputStream is piped directly to the backend via InputStreamEntity, avoiding AXIOM build. This mirrors NIO passthrough behaviour.

start() — accept loop replaces reactor start

PassThrough calls ioReactor.setExceptionHandler(...), then startPTTEndpoint(address, ioReactor, namePrefix) for each bind address — this schedules the reactor on its own thread. VT instead:

serverSocket = createServerSocket(bindAddress);
running.set(true);
state = BaseConstants.STARTED;
acceptThread = new Thread(this::acceptLoop, VTConstants.VT_THREAD_PREFIX + namePrefix + "-accept");
acceptThread.setDaemon(true);
acceptThread.start();

The accept thread is a single platform thread; handing off the accepted socket to a VT means it never blocks doing real work.

new acceptLoop()

while (running.get()) {
    Socket clientSocket = serverSocket.accept();
    clientSocket.setSoTimeout(soTimeout);
    clientSocket.setTcpNoDelay(tcpNoDelay);
    vtExecutor.submit(() -> handleConnection(clientSocket));
}

Why: this is the simplest possible accept pattern — the entire NIO reactor is replaced by one accept() + one VT dispatch. The IOException check after accept distinguishes normal shutdown (caused by serverSocket.close() in stop()) from actual errors.

new handleConnection(Socket)

Http1Config h1Config = Http1Config.custom().setBufferSize(VTConstants.STREAM_BUFFER_SIZE).build();
conn = new DefaultBHttpServerConnection(scheme.getName(), h1Config);
conn.bind(clientSocket);
BasicHttpContext context = new BasicHttpContext();
context.setAttribute(VTConstants.CTX_REMOTE_ADDRESS, clientSocket.getRemoteSocketAddress());
context.setAttribute(VTConstants.CTX_LOCAL_ADDRESS,  clientSocket.getLocalSocketAddress());
context.setAttribute(VTConstants.CTX_LOCAL_PORT,     clientSocket.getLocalPort());
while (conn.isOpen()) {
    httpService.handleRequest(conn, context);
}

Why the loop: HTTP keep-alive. handleRequest() processes exactly one request/response cycle and returns. HttpCore 5 keeps the connection open based on Connection: / HTTP/1.1 semantics; we simply keep calling until the socket is dead. The remote / local address is stashed in HttpContext so the worker can retrieve it without holding a socket reference.

changed stop()

PassThrough shuts down the reactor and endpoints via PassThroughListeningIOReactorManager. VT instead:

  • Flip running.set(false)
  • serverSocket.close() — unblocks the accept loop
  • vtExecutor.shutdown() — existing VTs drain naturally
  • acceptThread.join(5000) — bounded wait
  • serviceTracker.stop() — same as before

identical getEPRForService(), getEPRsForService(), getSessionContext()

Copy-for-copy from the PassThrough listener — these are transport-agnostic.

identical addToServiceURIMap(), removeServiceFromURIMap()

Same logic as PassThrough's private helpers (removeServiceFfromURIMap <typo in original> corrected to removeServiceFromURIMap).

The key optimisation of the VT transport: take the raw client-socket InputStream (wrapped in VTInputStreamPipe) and shove it into an InputStreamEntity on the HttpClient 4 request. No AXIOM tree is built; bytes flow client → backend without ever hitting the JVM heap as objects.

Drops content-length, host, connection, transfer-encoding before they are copied to the outbound request. HttpClient computes / owns all four — passing them through creates duplicates or mismatches that the backend rejects.

PassThrough's implementation is empty. VT reads HTTPConstants.HTTP_METHOD and, if it's an HttpRequestBase, aborts it to release the pooled connection.

6.3 Function-level comparison

run() (NIO, on worker pool) → process() (VT, in-line)

ServerWorker is Runnable and is submitted to a pool. Its run() method walks the request, creates a MessageContext, and calls AxisEngine.receive(). It does not block on the response — the response is posted back asynchronously via submitResponse() called from PassThroughHttpSender.

VTBlockingServerWorker.process() is invoked synchronously by HttpCore 5's request handler; the whole mediation flow runs on this VT, including the backend call and response write. Structurally the method does:

  1. Parse request metadata from ClassicHttpRequest: method, URI, case-insensitive header map, duplicate-header detection into excessHeaders.
  2. Build MessageContext (createMessageContext()) — sets transport in / out, server-side flag, incoming transport name, transport headers, remote address from HttpContext.
  3. Mark REST vs SOAP vs entity-enclosing and call one of processEntityEnclosingRequest(true) / processNonEntityEnclosingRESTHandler(..., true). Both finish with AxisEngine.receive(msgContext), which fires the entire Synapse mediation sequence on this VT.
  4. Safety net in finally: if the sender never populated a response (e.g. exception), write a default one so HttpCore 5 has something to serialise. 500 + plain-text if the last-resort call itself fails.
  5. Thorough cleanup:
    • Mark IN and OUT operation contexts setComplete(true) and cleanup()
    • Remove ServiceGroupContext from the ConfigurationContext cache
    • Strip heavyweight properties (PASS_THROUGH_PIPE, TRANSPORT_HEADERS, …)
    • MessageContext.destroyCurrentMessageContext() — clears the ThreadLocal
Why cleanup is explicit here. In NIO, the reactor thread is long-lived and Axis2 releases state as connection events arrive. In VT, the VT ends when process() returns — but the MessageContext ThreadLocal and the OperationContext references on ConfigurationContext are not automatically reaped (they'd leak the whole Synapse config). Explicit cleanup is the only reliable hook.

new submitResponse(MessageContext responseMsgCtx)

Called by VTHttpSender.submitResponse() during the respond phase. Writes back onto the ClassicHttpResponse:

  1. Status code — from PassThroughConstants.HTTP_SC (Integer or String)
  2. Reason phrase — from PassThroughConstants.HTTP_SC_DESC
  3. Transport headers — skipping VTConstants.HOP_BY_HOP_HEADERS
  4. Body — three branches:
    • NO_ENTITY_BODY=true → just status + headers
    • VT_INPUT_STREAM_PIPE present and builder not invoked → bodyStream.readAllBytes() into ByteArrayEntity (pass-through response)
    • Otherwise — build via MessageFormatterDecoratorFactory.createMessageFormatterDecorator() and formatter.writeTo()
  5. Set responseSent = true so the finally safety net doesn't double-write.

The content-type inference, SOAP envelope bootstrap, REST vs SOAP routing logic is ported nearly verbatim from PassThrough's ServerWorker. Key change: after identifying the body, it wraps httpRequest.getEntity().getContent() in a VTInputStreamPipe and stashes it on PASS_THROUGH_PIPE.

    public InputStream getInputStream() { return inputStream; }
}

Why it is still wrapped instead of storing the raw InputStream: the Synapse mediator code checks msgContext.getProperty(PASS_THROUGH_PIPE) and branches on type. Having a dedicated wrapper class makes instanceof VTInputStreamPipe checks in VTHttpSender and VTBlockingServerWorker unambiguous — we never confuse it with a bare InputStream accidentally set elsewhere.

8. VirtualThreadWorkerPool (new adapter)

File
vt/VirtualThreadWorkerPool.java
Implements
org.apache.axis2.transport.base.threads.WorkerPool

Axis2's WorkerPool interface is what the engine uses to submit Runnables (mediator dispatches, error handlers, timers, etc.). The default impl, NativeWorkerPool, wraps a ThreadPoolExecutor with a fixed worker count. That bottlenecks the entire engine once the pool is saturated.

VirtualThreadWorkerPool satisfies the same interface but backs it with a virtual-thread-per-task executor (typically the one owned by the VT listener). Every execute(Runnable) spawns a fresh VT:

public class VirtualThreadWorkerPool implements WorkerPool {
    private final ExecutorService executor;
    public VirtualThreadWorkerPool(ExecutorService executor) { this.executor = executor; }
    public void execute(Runnable task) { executor.submit(task); }
    public int getActiveCount() { return -1; }     // VTs don't expose this
    public int getQueueSize()   { return 0;  }     // no queue — immediate dispatch
    public void shutdown(int timeout) {
        executor.shutdown();
        try { executor.awaitTermination(timeout, TimeUnit.SECONDS); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

Why no direct counterpart: NIO uses NativeThreadFactory directly against a ThreadPoolExecutor. That mapping doesn't make sense here — VTs are so cheap that queueing is pointless.

Why getActiveCount() returns -1: the JDK doesn't expose live counts for VT executors without expensive thread-dump APIs. The metric is used only for diagnostics, so -1 is the documented "unknown" sentinel.

9. VTConstants vs PassThroughConstants

Mandatory: cacheHttpClient=true. Without it VTHttpSender.init() does not build the pooled CloseableHttpClient, and sendStreamedRequest() throws an AxisFault.

11.3 Known limitations (first cut)

  • HTTPS not yet wired — SSL listener is a follow-up.
  • JMX MBeans not registered — metrics object is created but not exposed.
  • Stream interceptors / wire logging not wired — can be added as HttpCore 5 interceptors.
  • WSDL GET-request processor not integrated — affects ?wsdl endpoints on the VT listener only.
  • Inbound endpoint managers calling PassThroughInboundEndpointHandler.getPassThroughSourceConfiguration() still expect the NIO transport. Running VT alongside NIO avoids this; VT-only deployments need the NIO listener disabled and the inbound endpoint manager updated to ask for the VT source configuration.
  • Correlation log / tenant initiator is a trivial backport once the core flow is green.

11.4 Behavioural parity with NIO (validated by branch-level tests)

  • Zero-copy body streaming triggers on the same mediator shapes as NIO (<call/> without content-aware predecessor). See CallMediator.isContentAware()=false.
  • A <log/> (any level except message_template / custom) before <call/> forces an OM build, same as NIO.
  • Response body from the backend flows through TRANSPORT_IN identically to AbstractHTTPSender.
